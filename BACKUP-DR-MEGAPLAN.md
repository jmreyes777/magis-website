# Backup & Disaster Recovery Megaplan (BDR)

Fifth megaplan, after security, speed, SEO, and observability. Observability
tells us **when** something breaks; this plan makes sure we can **recover what
was lost**. Today nothing protects the data: one bad script, one compromised
key (we already rotated one), or one fat-fingered console action against
Firestore is permanent. That is the biggest operational risk left in the
system while production cutover is pending.

## Philosophy

- **App-level, same-credential backups.** The backup engine uses the exact
  firebase-admin credential the backend already runs on — no new IAM roles, no
  GCP console dependencies (lesson learned from the TTL saga: console/IAM
  friction is where plans stall). Native GCP scheduled backups become a second
  layer later, during the prod pass, when the one-time IAM grant happens anyway.
- **3-2-1, adapted.** Three copies of business data: live Firestore, compressed
  snapshots in Firebase Storage, and a pulled mirror on the shop PC. Two media
  (cloud bucket + local disk). One copy off-provider (the local mirror; a
  second cloud target is a stretch goal).
- **A backup that has never been restored is a hope, not a plan.** Restore
  tooling ships in the same wave as backup tooling, a drill runs immediately,
  and drills repeat quarterly (calendared in the runbook).
- **Backups are observable.** Every run reports to Telegram (failure = alert,
  success = one-line heartbeat) and surfaces on the admin Observability page.
  Silence is treated as failure.
- **No plaintext secret dumps, ever.** Config/secrets are inventoried by KEY
  NAME + hash (drift/loss detection); the values themselves live only in the
  password manager + sealed offline copy per the runbook.

## Explicitly out of scope (by design, documented so nobody wonders later)

| System | Decision | Rationale |
|---|---|---|
| Redis | NOT backed up | Pure ephemera: rate-limit counters, alert throttles, revocation JTIs. Loss = counters reset; revoked-but-unexpired tokens briefly live again — acceptable because token TTLs are short. Noted in runbook as a post-restore security consideration. |
| Code | GitHub is the backup | Plus every dev clone. Runbook covers GH account-recovery hygiene (2FA recovery codes offline). |
| Prerender snapshots / build artifacts | NOT backed up | Regenerated by every build from source. |
| Facebook-derived media (album cutouts) | Manifest only | Re-derivable from the FB pipeline; losing them costs a re-run, not data. |

## Waves

| Wave | What | Where |
|---|---|---|
| BDR0 | **Recon & decisions**: collection census (names, doc counts, approx bytes, subcollection map), Storage bucket census (object count, total bytes, prefix breakdown). Finalize RPO/RTO + retention against real numbers. | one-off recon via backend credential; results recorded in this doc |
| BDR1 | **Backup engine**: recursive Firestore walk → one gzipped JSONL file per collection group + `manifest.json` (per-collection doc counts, byte sizes, content hash, duration, engine version) → uploaded to Storage under `backups/firestore/YYYY-MM-DD/`. Streamed batch reads (500/page) so backend RSS stays flat. Serializes Timestamps/GeoPoints/References losslessly. Retention pruning in-run: keep 30 dailies + 8 Sunday weeklies. | `backend/scripts/firestore-backup.js` (runnable standalone AND callable in-process) |
| BDR2 | **Trigger + alerting**: `POST /api/backup/run` guarded like the incidents endpoint (X-Obs-Auth secret or superadmin JWT); the edge worker's existing `*/5` cron fires it once daily at 03:0x Asia/Manila (19:0x UTC) with a KV once-per-day guard; manual pre-deploy snapshots via the same endpoint. Telegram: failure alert (throttled) + daily success heartbeat (`backup ok · N docs · M MB · Ss`). Last-run status doc (`backups/status`) rendered as a card on the admin Observability page. | `backend/routes/backup.js`, `server.js` mount, `magis-edge-worker/index.js` cron block, `admin-frontend` Observability card |
| BDR3 | **Restore tool + immediate drill**: `firestore-restore.js` — `--list` (available snapshots), default dry-run (what would be written), `--into-prefix drill_` (safe parallel restore), `--in-place --yes-i-know` (guarded, per-collection filter required). Drill = restore latest snapshot into `drill_*`, verify doc counts + spot-check hashes against manifest, then clean up. Run the drill as part of this wave and record evidence here. | `backend/scripts/firestore-restore.js` |
| BDR4 | **Storage bucket backup**: every run writes an object manifest (path, size, md5, contentType). If BDR0 census says the non-derivable set is modest, incrementally mirror new/changed objects into `backups/storage-objects/` (md5-keyed, no re-upload of unchanged). | extension inside `firestore-backup.js` run |
| BDR5 | **Off-cloud copy**: `backup-pull.js` mirrors the latest N snapshot folders to the shop PC (`C:\magis-backups\`), verifies manifest hashes after download, prints a one-line result. Scheduled weekly via Windows Task Scheduler (documented click-path) or run manually. | `backend/scripts/backup-pull.js`, runbook section |
| BDR6 | **Config & secrets inventory**: each backup embeds key-NAME manifests — `backend.env` keys, worker bindings (from `deploy-api.mjs` config), Render env keys (manual paste once, drift-checked thereafter) — values hashed, never stored. Runbook: password-manager entry + sealed printed copy for the two root secrets (Firebase SA key, Telegram bot token), GH recovery codes offline. | manifest step + `DR-RUNBOOK.md` |
| BDR7 | **Runbook + drill calendar**: `DR-RUNBOOK.md` with exact commands per scenario: (a) accidental collection wipe → in-place restore; (b) subtle corruption found late → point-in-time restore from dated snapshot; (c) Firebase project loss → new project rebuild sequence (SA key, TTL policies, restore, env rewire); (d) Render loss → redeploy from repo + env from password manager; (e) worker loss → `deploy-api.mjs` re-deploy; (f) this-PC loss → what the cloud + password manager recover. Quarterly drill calendar + drill log. Prod-pass stretch: native Firestore scheduled backups (one `gcloud` command / console visit) as the managed second layer. | `DR-RUNBOOK.md` |

## BDR0 census results (2026-07-15)

**Firestore** (default db): 18 top-level collections, **3,679 docs**, no
subcollections detected (engine walks recursively anyway — future-proof).
Bulk of the data: `messages` 3,241 · `auditLogs` 255 · `conversationKeys` 71 ·
`mfa_sessions` 43. Everything is backed up (no excludes — even the TTL'd
telemetry collections cost nothing at this size).

**Storage** (`magis-website.firebasestorage.app`): 185 objects, **12.6 MB**,
all under `media/`. Small enough that BDR4 upgrades from "manifest only" to a
**full incremental md5-keyed mirror** of the bucket.

**Sensitivity note:** snapshots contain `conversationKeys` (chat encryption
keys) → **backup archives are secrets**. The Storage backups prefix is
admin-SA-only; the off-cloud mirror (BDR5) must live on an encrypted/BitLocker
drive, and the runbook says so.

**Sizing:** full snapshot ≈ a few MB gzipped; worst-case retention footprint
(38 snapshots + mirror) well under 1 GB → storage cost is pennies. Daily run
expected to finish in ~1–3 min (dominated by per-doc subcollection probing).

## Targets (confirmed by census)

| Metric | Target | Notes |
|---|---|---|
| RPO (max data loss) | 24h | Daily 03:00 Asia/Manila snapshot; cheap to tighten later by upping cron cadence |
| RTO (collection wipe) | ≤ 1h | `firestore-restore.js --in-place`, from Storage snapshot |
| RTO (full project loss) | ≤ 1 day | New Firebase project + restore + env rewire per runbook |
| Retention depth | 30 daily + 8 weekly | Corruption discovered weeks late stays recoverable |
| Backup cost | ~pennies/month | Small collections; JSONL.gz in Storage; reads once daily |

|---|---|---|

| (dashboard) | `backups/status` doc stale > 26h → red card | admin Observability page |

## Verification (each wave lands with its drill)

1. BDR1: run backup → inspect Storage layout + manifest counts vs live counts.
2. BDR2: fire endpoint manually → Telegram heartbeat + dashboard card; confirm
   cron fire next morning.
3. BDR3: full drill — restore into `drill_*`, machine-verified counts/hashes,
   cleanup; evidence recorded in this doc.
4. BDR5: pull to `C:\magis-backups\`, hash-verified.
5. BDR7: tabletop walk-through of scenario (c) — every command exists, every
   secret's location named.
